## Key Findings Summary

### SC-001: Configuration Insights
- **5 mandatory fields** (id, host, port, username, password) — all require restart
- **20+ optional fields** with specific types and validation
- **TLV rules are per-connector**, not global (no value injection)
- **Restart enforcement is automatic** in CLI (stops/starts if required key changes)
- **No exponential backoff for reconnect** — fixed delay only

### SC-002: Lifecycle Insights
- **Add doesn't start** — must call Start separately
- **Start requires AMQP broker connected** — fails silently if not
- **Stop requeues pending messages** — critical for no message loss
- **Prefetch must be 1** — hardcoded for throughput control
- **Consumer tag reuse prevents duplicates** — prevents dark hole issue #234
- **Start only from NONE/UNBOUND states** — other states rejected

### SC-003: Reconnect Insights
- **No retry limit** — continues forever unless disabled or stopped
- **Fixed delay, no backoff** — 10s every time (intentional)
- **Two triggers:** connection failure and connection loss (same retry logic)
- **Stop cancels reconnect timer** — prevents restart after shutdown
- **Deferred reset on cycle** — allows multiple reconnect attempts in same factory
- **Session state race window** — undefined during reconnect window

### SC-007: Failover Insights
- **Sequence resets per message** — not round-robin (each message tries connector[0] first)
- **No connector type mixing in MO failover** — must be homogeneous
- **Availability = session count > 0** — no health check beyond this
- **Thrower iterates sequentially** — not random, not weighted
- **Billing shared across failover** — all connectors share same rate
- **No round-robin across messages** — each message starts from connector[0]

## Questions & Clarifications

**Q: Why does failover sequence reset per message?**  
A: Legacy behavior. Each message matches route (seq=-1), then thrower iterates from connector[0]. Not round-robin across messages.

**Q: Why no retry limit?**  
A: Legacy design. Retries forever; user disables via config flag if needed. No timeout.

**Q: Why must prefetch be 1?**  
A: Controls throughput. Each connector processes one message at a time (submit_sm_throughput).

**Q: Can MO failover mix http and smpps?**  
A: No. Design constraint: throwers are isolated by connector type.

**Q: What if SMPP broker not connected?**  
A: Add/Start fail silently (return False). User must ensure broker ready before add.
